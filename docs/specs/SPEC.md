# 內部採購與簽核 AI Agent 系統

> 本檔案只放**最終定案版本**。未定案的想法先寫進 `docs/specs/DRAFT.md`；每個功能區塊的討論過程
> 記在 `docs/ADR/discuss/<功能>.md`，修 bug 記在 `docs/ADR/debug/<功能>.md`；單一功能區塊若成長超過
> 約 200 行，把細節移到 discuss/ 或獨立附錄，這裡只留摘要 + 連結。

## 產品背景

模擬企業內部「需求 → 詢價 → 多供應商報價 → 綜合評選 → 簽核 → 採購單 → 收貨驗收 → 庫存」流程的 AI Agent 系統。情境設計成通用的內部採購場景（不掛靠任何特定產業），重點展示 AI 如何協助理解需求與整理資訊，同時由固定規則、權限、人工確認及稽核紀錄守住正式單據與決策。範圍涵蓋可完整展示的企業採購閉環；供應商 Portal、會計付款、完整合約管理及外部 ERP／EDI 串接不在目前範圍。

## 產品藍圖與功能規格

### 系統主流程

**狀態**：active
**討論紀錄**：`docs/ADR/discuss/main-flow.md`

**概要**：從 Vue 前端自然語言採購需求開始，經結構化確認、多供應商詢價、規格與品質門檻、固定公式綜合評選、人工選商、簽核、採購單、收貨驗收及庫存異動形成完整閉環。LLM 僅負責把語言轉為候選結構及生成人類可讀說明，不得直接計算正式金額、決定得標者或建立／修改正式單據。

```
[Vue：採購需求對話框] 自然語言建立／補充／修改多品項需求與候選供應商
      ↓
[n8n + LLM] 遮罩敏感資料 → 解析候選結構
      ↓
[Django + Vue] 驗證供應商、品項、數量、規格與版本 → 結構化確認
      ↓
[RFQ] 邀請多間供應商，各自建立獨立版本化報價
      ↓
[Django] 必要規格門檻 → 實際總成本、品質、交期、保固與履約固定公式評分
      ↓
[採購人員] 整單／逐項／拆量選商；系統只建議，不自動得標
      ↓
[簽核] 依得標後實際總成本路由、認領與決議
      ↓
[採購單] 核准後依得標供應商拆單，不在此時增加庫存
      ↓
[收貨／品質驗收] 僅合格數量寫入不可覆寫的庫存異動流水帳
      ↓
[Django] 全流程寫入 append-only 稽核紀錄並更新供應商品質／履約統計
```

**功能性需求**
- FR-1：Vue 前端提供自然語言詢價輸入表單，呼叫 Django API 觸發流程
- FR-1a：Vue 前端與 Django API 之間採 JWT 認證（access token 短效期、refresh token 長效期換發新 access token）；n8n 與 Django API 之間（含 Django 觸發 webhook、n8n 回呼）採固定 API Key 驗證自訂 header，不套用使用者登入流程
  - `login` 與 `auth/me` 必須回傳使用者所有生效角色合併後的 permission codes；Vue 導覽與 route guard 依權限碼判斷，不以單一 legacy role 推測業務權限
- FR-2：n8n Mask 節點於送出 LLM 前，向 Django API 取得當下合作中供應商清單，用清單做精確比對，比對成功才將供應商名稱、金額（含幣別）Token 化遮罩（如 `SUP_001`），並記錄當次請求有效的對照表；不遮罩數量欄位
- FR-2a：LLM 解析完成後，n8n Unmask 節點立即用對照表還原供應商真實名稱；還原後的所有後續步驟（查詢、試算、生成摘要）一律使用真實資料，不再遮罩
- FR-2b：遮罩比對失敗依情境分流處理：
  - 清單中查無此供應商 → 不送 LLM、不進複核佇列，即時回覆使用者「查無供應商，請確認名稱或先建檔」
  - 模糊比對（相似但非精確比對）→ 寫入「待人工複核」佇列，流程中止，待人工確認供應商身分
  - 供應商比對成功但其他欄位（如金額）格式無法解析 → 不進複核佇列，即時回覆使用者請求修正格式重新輸入
- FR-3：n8n 呼叫 LLM 將自然語言需求解析為多品項、多候選供應商及必要／偏好規格的候選結構；資料不完整時允許對話補充與修改，每次修改後皆須由後端驗證並重新顯示完整結構化內容。Vue 不顯示工程 JSON，必須以可編輯的用途、供應商、品項、數量、單位、材質、尺寸與特色欄位呈現。主檔名稱唯一精確命中時自動對應；若 LLM 簡化品名，但使用者原句明確包含某個生效正式品名，且簡化名稱只能唯一對應該原句中的正式品名，也可安全補回正式品項；有多個可能值或只有泛稱時仍不得猜測，交由使用者選擇。解析完成後，候選供應商、正式品項與正數數量等試算必填資料若缺少或無效，須立即以紅色框線及欄位文字說明標示，補正後自動恢復；不得只用顏色傳達錯誤。每個候選品項須顯示由 AI 辨識結果組成的品項、數量、單位與可用規格摘要；此摘要不是逐字原文。未對應正式品項時須顯示明確警告與試算停用原因，使用者可手動選擇或移除。候選確認畫面須以品項 × 候選供應商矩陣呈現供應關係、有效價格及品質資格狀態；矩陣只供建單前確認，不等於正式報價，也不因缺少供應關係或價格直接阻擋草稿。移除任何品項前均須確認；移除後清除舊試算結果，移除最後一項時若已有後端草稿須一併刪除，並清空候選資料回到自然語言輸入畫面，顯示約 5 秒的重設提示。採購需求仍為 `draft` 時，候選供應商以未發出的 draft RFQ 保存；這只是內部草稿，不代表已正式邀價，也不得產生正式供應商報價、簽核或採購單。提交成功後必須清除目前輸入、候選結構、草稿與試算狀態，顯示含申請編號及「查看申請」入口的可關閉成功提示；提示預設約 5 秒後自動消失，避免使用者誤以為仍在編輯已送出案件或重複提交
- FR-4：Django service 以固定程式邏輯試算報價金額，LLM 不參與數字運算
- FR-4a：試算完成後，Django service 依供應商＋產品過去已核准且有效的採購單明細計算歷史均價與偏離百分比；無歷史紀錄時標示無法比較但不中止流程。Vue 以供應商卡片顯示逐項單價、小計、整體試算總額及「高於／低於／接近歷史均價」白話標籤，不只顯示偏離百分比或 JSON。某供應商全部品項皆無有效價格時，總額顯示「尚無報價」，不得以零元冒充有效試算結果。價格異常為資訊性提示，不取代必要規格檢查或人工選商
- FR-5：n8n 呼叫 LLM 依真實數字生成人類可讀的報價摘要文字
- FR-6：Django API 提供幻覺驗證端點，比對 LLM 生成文字中的數字與原始查詢值；不一致時寫入待人工複核佇列並中止流程
- FR-6a：待人工複核佇列一律指派給具有 `manual_review.decide` 權限的角色處理，不開放自由編輯 AI 生成內容後放行，僅提供以下有限選項：
  - 幻覺驗證失敗案件：核准（丟棄 LLM 生成的摘要文字，改用系統制式模板依真實數字組出文字，接續走簽核流程）或駁回（詢價作廢，通知申請人重新送出）
  - 供應商模糊比對案件：確認為系統疑似比對到的供應商（用確認後的供應商產生 Token，重新走正常遮罩→LLM 解析流程；此案件在 Mask 節點階段就中止，品項/數量/幣別尚未被 LLM 解析出來，不能跳過解析直接查詢報價）或駁回（通知申請人確認供應商全名後重新送出）
- FR-6b：複核案件的 Gmail 通知發送給所有具有 `manual_review.decide` 權限的使用者（非綁定單一人），複核頁面提供認領機制（處理中／未處理／已處理，含認領人），避免多人同時處理同一案件
- FR-6c：管理員在複核佇列的每個決定（核准/駁回、認領）都需寫入稽核 log
- FR-7：Django service 依金額判斷簽核層級並路由給對應簽核人，分三段門檻（小額 1 萬元以下、中額 1 萬～10 萬元、大額 10 萬元以上，門檻寫死在 Django 設定）
- FR-7b：簽核層級的金額邊界明確定義為：small `≤ 10,000`、medium `> 10,000 且 ≤ 100,000`、large `> 100,000`，避免 10,000 與 100,000 落入重疊區間
- FR-7a：簽核額度與目標角色由獨立 `approval_policies` 管理；路由邏輯依得標後實際總成本找出可涵蓋該金額且上限最低的有效政策，將案件指派給政策指定角色，建立當下不預先指定特定使用者；若沒有一般政策可涵蓋，路由至明確設定的最高額度業務簽核政策，不以系統管理員身分代替
- FR-8：n8n 透過 Gmail 節點通知該角色底下**所有**使用者（廣播，非單一人），附上簽核頁面連結
- FR-8a：簽核佇列以 `approval_cases`／`approval_steps` 為唯一正式簽核來源並提供逐關認領機制。符合當前關卡目標角色且同時具有 `approval.claim`、`approval.decide` 權限的使用者可認領；`approval_steps.claimed_by_id` 於認領當下才寫入。已認領關卡對同角色其他使用者顯示「處理中／已被 OOO 認領」，資料庫鎖定保證同時認領只有一人成功；前一關未通過不得跳關認領。legacy `approvals` 僅保留歷史唯讀，不再接受認領或決議
- FR-9：簽核工作區讀取 `approval_cases`，顯示申請編號、採購用途、申請人、簽核政策、總金額、案件狀態及各關卡順序、類型、角色、狀態與認領人。使用者只能操作自己具資格的當前關卡；認領後執行核准／駁回時必須輸入非空白理由。決議完成後保留認領人、決議人、理由與時間，不提供覆寫；legacy Quote 的 AI 摘要與價格偏離資訊不再作為新版簽核工作區的正式資料來源
- FR-9a：具有全域檢視或稽核權限者可查看全部簽核案件，但只有具備案件目標角色與 `approval.decide` 權限者才能認領與決議，不得因系統管理權限跨角色代簽；人工複核另由 `manual_review.decide` 權限控制
- FR-9b：申請人可查看自己建立的需求；「我的採購需求」以 `purchase_requests` 為資料來源，只列本人案件並依建立時間新到舊排序，至少顯示申請編號、用途、品項摘要、候選供應商摘要、申請人、建立時間與狀態，不與 legacy Quote 混在同一清單。清單採後端分頁，使用者可選每頁 10／20／50 筆、預設 20 筆，並顯示總筆數、目前頁數、總頁數及上一頁／下一頁；頁碼與每頁筆數保存在 URL。點擊申請編號時須在保留清單背景的彈窗顯示本人需求唯讀詳情，呈現用途、需求日期、幣別、申請人、時間、候選供應商及完整品項／規格，不提供操作；可由右上角關閉圖示、背景遮罩或 `Esc` 關閉，內容過長時只捲動彈窗。詳情網址仍保存案件 ID、原頁碼與每頁筆數，重新整理或直接開啟連結仍顯示同一彈窗；非本人案件統一視為不存在。草稿可修改或刪除，已提交但尚未完成簽核的案件可撤回並留下稽核紀錄。正式報價、得標、採購單、收貨與驗收紀錄不得直接覆寫或實體刪除，錯誤須以版本、取消、作廢或反向更正處理
- FR-10：最後一關簽核核准時，後端必須在同一 transaction 依得標供應商自動拆分一張 `draft` 採購單，並以需求、得標數量、規格與 TWD 分攤成本建立不受後續主檔異動的明細快照；若建單不完整，最終簽核決議必須回滾。只有具 `purchase_order.manage` 權限者可以版本檢查後正式發單；建單與發單都不得直接增加現有庫存或建立入庫流水，發單僅將訂購數量計入在途快照。供應商交貨後，具 `receipt.record` 權限者可對 `issued`／`partially_received` PO 建立分批、分品項收貨草稿；一般收貨累計不得超過訂購數量，送驗時依 `version` 防止重複提交、將實收數量自在途快照扣除並轉為 `inspecting`。具 `inspection.decide` 權限且不是該批收貨人者，必須一次完成整張收貨單的逐項品質驗收；每項合格、瑕疵與拒收數量須守恆，只有合格數量可在同一 transaction 建立 `receipt_accept` 流水並增加 on-hand。瑕疵與拒收數量必須透過正式差異案件拆量指定補交、退貨、折讓或短交結案；補交收貨須引用同一 PO 品項的有效補交明細，可超過原訂購量收貨上限但不得超過該明細核准量，且仍須重新驗收。所有 PO 品項累計合格數量等於訂購量後，PO 才轉 `received`；短缺已正式折讓或結案時可轉 `closed`，同需求所有 PO 均 received／closed 後需求才 completed，否則維持 partially_received
  - 正式差異案件送出後，處理類型、數量、理由與所屬案件不得覆寫或刪除；退貨、折讓與短交結案由採購人員以受控 command 完成且不異動未入庫庫存，replacement 不可人工完成，須在授權額度內補交、重新驗收，累計合格量達授權數量後由系統自動完成。每次完成均保存 actor、時間與稽核紀錄。差異案件僅能由 `open` 結案，且所有明細必須已 `completed`。補交收貨僅可引用同 PO 品項、案件仍為 `open` 且明細仍為 `pending` 的 replacement 授權
  - 品質驗收人只負責合格／瑕疵／拒收判定；具 `purchase_order.manage` 的採購人員負責差異案件草稿、送出、商務處理與結案。補交由 `receipt.record` 收貨後再交由不同人以 `inspection.decide` 驗收；`audit.read` 只讀
- FR-10a：庫存以不可覆寫的 `inventory_movements` 為真相來源、`inventory_balances` 為查詢快照；任何入庫、出庫、退貨或人工調整皆須保存類型、數量、原因與操作者。餘額異動後低於門檻且無未完成建議時，自動新增採購建議
- FR-10b：採購建議可轉為採購需求草稿並保留來源關聯；需求進入正式採購流程後將建議標示為處理中，完成有效採購或人工忽略後分別標示 processed／dismissed
  - 庫存位置以 `on_hand - reserved + in_transit` 計算；低於品項門檻時，建議數量為門檻與庫存位置的差額。同品項已有 pending／in_progress 建議時不重複建立
  - 具 `purchase_request.create` 權限者可指定候選供應商並轉為本人草稿；草稿正式提交後建議轉 in_progress，對應需求 completed 後轉 processed。只有 admin 可將尚未轉單的 pending 建議標記 dismissed
- FR-11：Django 於每次 AI 呼叫完整寫入稽核 log（操作者、時間、脫敏內容、查詢的資料表、驗證結果）
- FR-12：採購核心單據分為 `purchase_requests`、`rfqs`、`supplier_quotes`、`award_decisions`、`approvals`、`purchase_orders`、`goods_receipts`／`quality_inspections`；每個實體維護獨立狀態機，不以單一 `quotes.status` 混合所有階段
- FR-13：同一需求可包含多品項，同一 RFQ 可邀請多間供應商；正式發出時固定回覆期限、受邀供應商與評分規則快照，需求進入 sourcing。每間供應商維持獨立且版本化的報價與規格／商務條件快照，可只回覆可供應的部分品項；未回覆品項標示為未報價，不以零元代替
- FR-14：得標以逐項 `award_lines` 建模，支援整單同一供應商、逐品項選商及同品項拆量；得標數量加總必須等於有效需求數量
- FR-15：評選先以後端固定運算子判斷必要條件，再以案件快照權重計算實際總成本、規格品質、交期、付款條件、供應商表現及永續／風險分數。比較必須以同一需求品項為單位，稅額、運費與折扣依報價明細小計占比分攤後再彙總整張報價，不可直接以部分報價的整張總額與完整報價比較。未報價品項不給 0 分，部分報價可成為對應品項建議，但不得成為整單建議。缺少正式履約或永續資料時標示「尚無資料」並顯示資料完整度，不得使用假設中間分。必要條件不符或未提供者預設不得推薦；例外採用只能由具獨立權限者填寫理由並保存核准人與時間，後續在一般金額簽核之前加入採購主管例外簽核，且原 waiver 核准人不得再次決議同一例外。系統只標示各品項與整單的最高合格分數建議；同分並列，不自動決定得標者。非系統推薦者得標亦須填理由。AI 只解釋結果，不計算分數或決定得標者
- FR-16：供應商、品項、供應商產品／價格、庫存、採購建議、RFQ 比價、收貨驗收及稽核頁面提供受權限控制的操作；主檔採啟用／停用與價格版本，不任意實體刪除。供應商可提供資料，但必須由企業內部確認後才成為正式資料；目前不建立外部供應商 Portal
- FR-16a：功能模組導覽採左側單欄、由上而下的垂直階層；大分類與其子功能上下排列、子功能縮排，不將多個大分類橫向並排。分類可收合，側欄內容超出視窗時獨立捲動，桌面顯示固定側欄，窄螢幕改為可開關抽屜；只顯示目前使用者有權限存取的項目，並清楚標示所在頁面
- FR-16b：n8n v2 只將自然語言解析為可編輯候選結構，不計算正式金額、不選商且不直接建立正式單據；自然語言送往 n8n／LLM 前，必須先由 Django 固定程式遮罩供應商與金額等敏感資訊，回傳候選結構後再於單次請求流程內還原，不得將遮罩對照表持久化。使用者確認後才由 Django 建立 Purchase Request draft。Phase 5.0 應用切換期間，`POST /inquiries/trigger/`、`POST /quotes/calculate/` 與 `POST /quotes/verify-hallucination/` 已先停止寫入並統一回 `410 Gone`／`legacy_command_retired`；其餘 legacy Quote／Approval command 於簽核與人工複核切換新核心後停止。舊資料只保留歷史查閱與必要回退能力
- FR-17：正式單據保存品項規格、報價、幣別、匯率、稅額、運費、折扣、交期、保固及評選規則快照；草稿使用版本控制，提交使用 idempotency key，後端提交時重新驗證版本、價格與報價有效期限。供應商報價由後端以 Decimal 重算明細小計及換匯後實際總成本，不信任呼叫端總額；正式提交後不得原地修改，改版須將舊版標記 revised 並建立新 revision，同一邀請只能有一個有效版本
- FR-18：權限採多角色 RBAC 與職責分離；申請人不得核准自己的案件，系統管理員不因管理權限自動取得業務決議權。簽核路由以得標後實際總成本為準，waiver 獨立覆核須先於一般金額關卡，且原 waiver 核准人不得再次決議同一例外。關卡必須依序認領與決議，目前正式支援 `any_one` 決議模式；駁回時將 Approval Case、Award 與 Purchase Request 分別記為 `rejected`，不與主動取消的 `cancelled` 混用。認領、決議、選商、驗收與庫存異動皆須以 transaction 防止競態
- FR-19：舊 `quotes` 採新表並行與可逆資料遷移，保存 `legacy_quote_id`；切換新 API 後舊表先保留唯讀，Phase 4.1 不執行 DROP。舊 approved Quote 轉為遷移用已收貨／驗收紀錄，但不得再次增加既有庫存。舊系統沒有保存的核准人、收貨人或驗收人不得猜測或冒用他人；legacy snapshot 必須明確標記原紀錄缺失，且只有 legacy migration 收貨可使用空 actor 例外

**非功能性需求**
- NFR-1：安全 — 送往 LLM 的內容必須先脫敏（遮罩敏感欄位），且遮罩/還原邏輯以固定程式碼實作，不交由 LLM 判斷；遮罩對照表僅於單次請求流程中暫存，不落地存 DB
- NFR-2：可信度 — 幻覺驗證比對邏輯為固定程式碼，AI 無法修改或跳過；驗證失敗案件不得直接顯示給一般使用者
- NFR-3：一致性 — 正式金額、得標、簽核、驗收與庫存異動由 Django transaction 與資料庫約束保證；LLM／n8n 失敗不得留下半套正式單據
- NFR-4：可追溯性 — 正式單據使用不可變快照，稽核紀錄與庫存流水採 append-only；錯誤以新版、取消、作廢或反向更正處理

### 權限管理

**狀態**：active
**討論紀錄**：`docs/ADR/discuss/permissions.md`

**概要**：採多角色 RBAC 與職責分離，以權限能力控制需求、RFQ、選商、簽核、收貨、驗收、主檔、庫存與稽核操作。

**功能性需求**
- FR-1：一般員工可建立、修改或刪除自己的需求草稿，並提交為正式採購流程；不得修改或實體刪除已形成的正式報價、得標、採購單、收貨與驗收紀錄
- FR-1a：一般員工可查看自己的需求與狀態，並依系統主流程 FR-9b 撤回尚未完成簽核的案件；不得查看他人案件
- FR-2：簽核人僅能看到自己角色與權限範圍內的案件，簽核額度依 `approval_policies` 路由（詳見系統主流程 FR-7a）
- FR-3：全域資料檢視與稽核 log 分別由明確權限控制；系統管理員不因管理帳號／權限而自動取得全部業務資料或決議權
- FR-4：角色與權限使用 `roles`、`permissions`、`user_roles`、`role_permissions` 多對多模型，不在 API／View 硬寫角色名稱；簽核額度屬簽核政策，與系統管理權限分離
- FR-5：JWT payload 僅放使用者 ID，不放角色、權限或簽核金額上限等易變資料；每次請求即時查詢有效角色與權限
- FR-6：前端登入使用 Email＋Password；access token 採短效期並僅保存在前端記憶體，refresh token 以 HttpOnly、SameSite Cookie 保存並啟用 rotation 與撤銷機制。登入失敗不得透露 Email 是否存在
- FR-7：申請人不得核准自己的案件；系統管理員不自動取得選商、簽核、驗收或庫存調整等業務決議權

**非功能性需求**
- NFR-1：安全 — 不適用（demo 系統，非高流量情境）

| --- | --- | --- |
| 詢價中提到的供應商不在系統供應商清單內 | Mask 節點比對合作中供應商清單，比對不到即攔截 | 不送 LLM、不進複核佇列，即時回覆使用者「查無供應商，請確認名稱或先建檔」 |
| 詢價中供應商名稱與清單模糊相似但非精確比對（如漏字、簡稱） | 相似度比對不到精確結果時，不自動猜測身分 | 寫入「待人工複核」佇列，流程中止；管理員確認供應商身分後，用確認後的供應商重新走正常遮罩→LLM 解析流程（此時品項/數量/幣別尚未解析出來，不可跳過解析直接查詢） |
| 詢價中金額等欄位格式無法解析（如中文數字「五萬」） | 供應商比對成功但其他欄位解析失敗時，不進複核佇列 | 即時回覆使用者請求修正格式重新輸入，不中止整體流程 |
| LLM 生成的報價摘要文字中的數字與原始查詢值不一致（幻覺） | Django 固定比對邏輯逐一核對摘要文字中的數字 | 寫入「待人工複核」表，流程中止，不直接顯示給簽核人或申請人 |
| 待複核案件負責的管理員剛好無法即時處理 | Gmail 通知發送給所有管理員角色使用者，而非綁定單一人 | 任一管理員可認領處理，複核頁面標記認領狀態避免重複處理衝突 |
| 一般簽核案件路由到的角色，該角色底下使用者剛好都沒空即時處理 | Gmail 通知發送給該角色底下所有使用者，而非綁定單一人（`approvals.approver_id` 建立時為 null） | 任一符合資格的使用者可認領處理，簽核佇列頁面標記認領狀態避免重複處理衝突 |
| 採購金額超過所有一般簽核政策的金額上限 | 路由至明確設定的最高額度業務簽核政策，不以系統管理員代簽 | 找不到任何有效政策時阻止提交並通知權限管理者補正政策 |
| 該供應商＋產品組合過去沒有已核准採購紀錄，無法比較歷史均價 | FR-4a 查無歷史紀錄時直接跳過比對 | 不標記價格異常，不中止流程，正式報價明細的價格偏離記為 null |
| 必要規格不符合或供應商未提供證明 | 必要條件先於加權評分檢查，預設排除推薦 | 若仍要採用，必須填寫例外理由並走額外核准及稽核 |
| 採購人員選擇非系統推薦報價 | 系統不阻止人工選商，但要求說明理由 | 保存選擇理由、操作者、評分快照與核准結果 |
| 報價過期、價格版本變動或草稿版本已落後 | 提交時由後端重新驗證報價有效期限、價格與版本 | 拒絕舊提交並要求重新試算／確認，不建立正式單據 |
| 重複點擊提交或相同請求重送 | 使用 idempotency key 與資料庫唯一約束 | 回傳同一處理結果，不重複建立需求、報價或採購單 |
| 採購單尚未到貨或驗收不合格 | 核准只建立採購單，不直接入庫 | 僅驗收合格數量寫入庫存流水；拒收／退貨另建反向異動 |
