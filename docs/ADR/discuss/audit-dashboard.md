# 稽核與正確率總覽 討論紀錄

> 同一功能的多次討論都寫在同一個檔案，依時間往下附加新段落，不要開新檔案。

## 2026-08-24 [標籤：使用者] 是否需要一個頁面呈現「AI 與真實資料比對」的正確率

**狀態**：superseded（決策 2「幻覺驗證通過率」卡片已被本檔 2026-09-02〈改採現行流程健康指標並移除歷史幻覺卡片〉條目移除；「新增獨立功能區塊」「供應商比對準確率」「複核佇列處理狀況」「僅管理員可見」等其餘決策仍有效，見下方各條目）

**背景**：原始規格只有「稽核 log 查詢頁」，可以查單筆紀錄，但沒有任何統計/量化呈現，無法回答「這套遮罩＋驗證機制實際運作得好不好」這個問題。

**討論內容**：每次幻覺驗證、每次供應商比對，都已經寫進稽核 log（FR-6、FR-11），資料基礎已經存在，只是缺一層統計聚合。討論後認為這個頁面跟專案核心賣點（AI 輸出可信度）直接相關，值得獨立列一個功能區塊，而不是塞進既有的稽核 log 查詢頁面裡混著看。

**決策**：
1. 新增獨立功能區塊「稽核與正確率總覽」，統計來源全部是既有稽核 log 資料，不需要新增資料表。
2. 頁面呈現三類統計：
   - 幻覺驗證通過率（一致 vs 不一致的比例）
   - 供應商比對準確率（精確比對／模糊比對／查無供應商三種情況的次數與比例）
   - 複核佇列處理狀況（待處理筆數、已處理筆數，處理結果分布）
3. 權限比照稽核 log，僅管理員可見。

**理由**：這個頁面把「攔截問題案件」的機制從單次事件提升成可持續監控的量化指標，對於展示「AI 導入企業系統要能持續監控、不是做完驗證就結束」這個主題有直接幫助，且不需要新增資料模型，實作成本低。

**後果**：
- Django 需要提供一個統計聚合 API（依稽核 log 計算比例），前端 Vue 頁面呼叫呈現。
- 統計期間篩選（例如本週/本月）留到實作階段再定，SPEC 先定案「有這個頁面、呈現哪三類統計」。

## 2026-09-02 [標籤：使用者] 正式納入 Phase 6

**狀態**：accepted

**背景**：此功能已於 2026-08-24 定案，但 SPEC 的實作階段長期保留「Phase 1：待補」，建立 Phase 5～7 Roadmap 時也未排入任何階段。

**討論內容**：資料來源與正式採購 API 契約已於新核心建立，剩餘工作同時涉及 Django 統計聚合端點與 Vue 儀表板頁面，性質與 Phase 6 企業操作介面一致。

**決策**：「稽核與正確率總覽」正式併入 Phase 6，不另立新 Phase，也不回溯擴張已結案的 Phase 5。Phase 6 必須完成聚合 API、儀表板、統計期間篩選、空資料／錯誤處理、權限驗證與瀏覽器驗收，才能宣稱此功能完成。

**理由**：這是具有後端支援的可視化功能，與 Phase 6 的導覽、權限與各角色瀏覽器流程同步實作，可避免重複調整介面與驗收基礎。

**後果**：原 DRAFT 的待決排程項目移除；SPEC 與 PROGRESS 將此功能明列為 Phase 6 正式範圍。

## 2026-09-02 [標籤：AI] 實作階段發現：FR-1／FR-2 的資料來源現況與處理方式

**狀態**：superseded

**背景**：實作聚合 API 時發現，Phase 5.0 起 `inquiries/parse` 已改為 Django 固定邏輯直接驗證候選供應商／品項，不再產生需要比對的 AI 生成敘述文字；`services/masking_service.py` 目前也只在「模糊比對」（含多筆精確命中的歧義）案件寫入 `manual_review_queue`，「精確比對」與「查無供應商」兩種結果並未落地保存到任何資料表。這代表 FR-1（幻覺驗證通過率）沒有新資料持續寫入，FR-2（供應商比對準確率）也無法計算三種情況的完整佔比。

**討論內容**：與 Robin 確認 FR-1 卡片的處理方式，選項為（a）保留卡片、標註僅涵蓋 Phase 5 切換前的歷史資料，或（b）這次先不做、之後有需要再補。Robin 選擇 (a)。FR-2 的對稱情形（供應商比對只有模糊比對案件有資料）沿用相同保守原則處理，不另外詢問。

**決策**：
1. FR-1 幻覺驗證通過率：保留卡片，資料來源鎖定 `audit_logs`（`action_type="hallucination_check"`）既有歷史紀錄，畫面加註明確說明「僅涵蓋 Phase 5 切換前的歷史資料，新流程不再產生」。
2. FR-2 供應商比對準確率：只呈現「模糊比對」數量與其處理結果分布（待處理／核准／駁回），並加註「精確比對與查無供應商未持久化，無法計算三種情況的整體佔比」，不修改 `masking_service.py` 新增稽核寫入（避免在 Phase 6 前端建置期間變動屬於 100% 覆蓋率要求的資安核心邏輯）。
3. 兩張卡片皆不新增資料表或修改既有寫入邏輯，只依現有 `audit_logs`／`manual_review_queue` 資料聚合。

**理由**：誠實呈現系統現況優先於為了湊出「完整比例」而新增未經確認的產品邏輯；FR-11（每次 AI 呼叫寫入稽核 log）與遮罩服務的稽核記錄範圍是否需要擴充，屬於獨立的產品/安全決策，不應該在 Phase 6 前端建置的過程中順帶展開。

**後果**：
- `services/audit_dashboard_service.py` 的 `hallucination_check`／`supplier_match` 回應各自帶 `note` 欄位說明資料侷限，前端儀表板頁面需原樣呈現此說明文字。
- 若之後要讓這兩張卡片反映持續更新的資料，需要另外對 `masking_service.py`（供應商比對三種結果）與新版 inquiries/parse 流程（是否仍需要類幻覺驗證機制）做獨立產品決策，屬未來待辦，記錄於此供後續參考，暫不寫入 DRAFT.md（非待排程項目，只是既有 Phase 6 決策的補充說明）。

## 2026-09-02 [標籤：使用者] 改採現行流程健康指標並移除歷史幻覺卡片

**狀態**：accepted

**背景**：使用者進一步確認後認為，只會停留在 Phase 5 切換前歷史資料的卡片無法反映目前系統狀況，會讓面試展示與實際管理判讀產生誤解。

**討論內容**：比較「繼續標示歷史資料」與「讓舊資料退出現行總覽」後，決定保留歷史稽核紀錄及 legacy Model／Migration，但現行儀表板只顯示持續更新且能採取行動的指標。

**決策**：
1. 頁面改名為「採購稽核與流程健康總覽」，移除幻覺驗證通過率卡片。
2. `inquiries/parse` 回傳具時效且綁定使用者的簽章候選憑證；第一次建立草稿時由 Django 比較候選與確認內容，寫入直接採用／人工修正及修正欄位類別，不保存原始文字或欄位值。
3. 解析階段另寫入供應商與品項命中／未命中的純數量彙總；既有模糊比對複核統計繼續保留。
4. 儀表板同時呈現人工複核、價格異常及正式品質驗收合格率。既有 `hallucination_check` 稽核資料只留在稽核紀錄查詢，不刪除、不遷移。

**理由**：現行儀表板應回答「現在流程是否健康」，而不是展示不再成長的舊機制；簽章候選讓採用／修正判定由後端完成，避免信任前端自報，同時維持 demo 所需的隱私邊界。

**後果（補充）**：本條目取代 2026-08-24 條目中「幻覺驗證通過率」卡片的決策，該條目狀態已同步標記為 `superseded`。

**後果**：不新增資料表或 Migration；沿用 `audit_logs` 的現有欄位儲存去識別化 JSON 彙總。先前 2026-09-02「保留歷史幻覺卡片」決策由本段取代。
