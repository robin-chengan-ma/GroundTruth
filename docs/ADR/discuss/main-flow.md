## 2026-08-24 [標籤：使用者] 遮罩規則、還原時機與遮罩失敗 fallback

**狀態**：accepted

**背景**：原始構想文件只寫「固定 regex 遮罩供應商名稱、金額」，沒有定義具體遮罩欄位、Token 化方式、還原時機，以及比對不到供應商時的 fallback 邏輯，開發前必須先定案。

**討論內容**：
- 遮罩欄位：討論是否要遮數量，決定不遮，因為數量不算敏感商業資訊，遮罩過多會降低 LLM 解析自然語言的準確度。
- 遮罩方式：比較「單純字串替換」vs「Token 化 + 對照表」，字串替換在供應商名稱有包含關係時（如「協興」vs「協興五金」）容易替換錯位。
- 還原時機：流程中有兩個 LLM 節點（解析、生成摘要），討論後確認只有「詢價原文 → 送第一個 LLM 解析」這段需要遮罩，因為目的是避免使用者原始輸入的敏感字串被外部 LLM 看到；解析後立即用對照表還原，後續查詢、試算、生成摘要全程使用真實資料，因為這幾步的目的是避免 LLM 算錯數字/亂寫文案，不是資料外洩問題。
- Fallback 邏輯：原本只討論「regex 沒抓到就進複核佇列」，後續深入討論後，改用「比對系統既有供應商清單」取代純 regex 猜測，並依情境分流，避免把單純輸入格式問題也塞進人工複核佇列。

**決策**：
1. 遮罩欄位：供應商名稱、金額（含幣別）。不遮數量。之後新增聯絡人、Email 等個資欄位時，比照辦理。
2. 遮罩方式：Token 化。Mask 節點先向 Django API 取得當下合作中的供應商清單，用清單做精確比對，比對成功才換成當次請求有效的 Token（如 `SUP_001`）並記錄對照表；LLM 解析完成後立即用對照表還原，後續步驟一律使用真實資料。
3. 遮罩失敗 fallback 依情境分流，取代單一「進複核佇列」的處理：
   - 情境 A（查無此供應商，清單裡完全比對不到）：不送 LLM、不進複核佇列，直接回覆使用者「查無供應商，請確認名稱或先建檔」。
   - 情境 B（模糊比對，如「協興」對到「協興五金」但非精確比對）：進「待人工複核」佇列，因涉及金流風險，不自動猜測身分。
   - 情境 C（供應商比對成功，但金額等其他欄位格式無法解析，如中文數字「五萬」）：不進複核佇列，直接回覆使用者請求修正格式重新輸入。
   - 只有情境 B 才真正動用「待人工複核」佇列；情境 A、C 屬於輸入問題，由系統即時回覆使用者自行修正，避免複核佇列被非 AI 風險案件塞滿。

**理由**：分流可以讓「待人工複核」佇列真正聚焦在「有金流風險、AI 無法安全判斷」的案件，而不是被單純的輸入格式錯誤淹沒；Token 化搭配供應商清單比對，比純 regex 猜測更準確，也更容易向面試官解釋設計依據（「拿系統既有資料做比對」而非「憑經驗寫 regex」）。

**後果**：
- Mask 節點需要在遮罩前先呼叫 Django API 查詢供應商清單，增加一次 API 呼叫，但可接受。
- 需要在 CRM 供應商資料表之外，額外設計一個「當次請求有效」的 Token 對照表（不需要落地存 DB，n8n workflow 執行期間的暫存變數即可）。
- 情境 A、C 的即時回覆邏輯需要在 Django API 層（或 n8n）提供對應的錯誤訊息端點，等實作階段補齊 API 規格。

## 2026-08-24 [標籤：使用者] 待人工複核佇列的處理者、接回主流程方式與通知範圍

**狀態**：accepted

**背景**：原始構想文件只寫「不一致 → 寫入待人工複核表，流程中止」，沒有定義誰處理、處理完怎麼接回主流程，也沒考慮負責處理的人剛好無法即時處理時該怎麼辦。

**討論內容**：
- 處理者：目前系統只有員工/簽核人/管理員三種角色，討論後決定不新增「複核人員」角色，直接歸給管理員（管理員原本就有「可見全部＋稽核 log」的權限層級，複核本來就需要看到完整原始資料）。
- 接回主流程的方式：複核案件分兩種來源（幻覺驗證失敗、供應商模糊比對），討論後決定管理員只能在「有限選項」裡做決定，不開放自由編輯 AI 生成內容後放行，避免削弱驗證機制的公信力。
  - 幻覺驗證失敗：管理員看到「LLM 生成摘要」vs「原始真實數字」並列對照，選擇核准（丟棄有問題的 LLM 文字，改用系統制式模板組出的文字接續走簽核流程）或駁回（詢價作廢，通知申請人重新送出）。
  - 供應商模糊比對：管理員看到「使用者輸入原文」vs「系統疑似比對到的供應商」，選擇確認為該供應商（流程從查詢供應商報價那一步繼續，不重跑 LLM 解析）或駁回（通知申請人確認供應商全名後重新送出）。
- 負責人不在的風險：討論了三個方案——(A) 不處理，案件卡著；(B) 通知所有管理員角色使用者，誰先看到誰處理，搭配認領機制避免重複處理；(C) 加上逾期自動升級通知機制。(A) 會讓流程實質停擺，跟系統設計初衷矛盾；(C) 需要額外的排程/計時器基礎設施，複雜度超出「深度夠用即可」的範圍。

**決策**：
1. 複核案件一律指派給管理員角色處理，不新增額外角色。
2. 管理員的決定只有「核准（依案件類型走系統安全路徑）」或「駁回」兩種，不開放自由編輯 AI 生成內容後放行。
3. Gmail 通知範圍改為「所有管理員角色使用者」，而非綁定單一人，並搭配認領機制：管理員打開複核頁面即標記該案件「處理中／已被 OOO 認領」，避免多位管理員同時處理同一案件造成衝突決議。
4. 逾期自動升級通知機制（方案 C）暫不實作，記入 `docs/specs/DRAFT.md` 作為未來加分項。
5. 管理員在複核佇列的每個決定都需寫入稽核 log，比照其他 AI 呼叫紀錄。

**理由**：通知所有管理員 + 認領機制，用最低的實作成本解決「單點失聯」的風險，不需要額外排程基礎設施；核准/駁回的有限選項設計維持「驗證邏輯不可被人工繞過」的一致性。

**後果**：
- 需要在使用者資料表上能篩選出「管理員角色」的所有使用者清單，供 n8n Gmail 節點群發通知。
- 複核頁面需要「認領」狀態欄位（處理中／未處理／已處理，含認領人），避免併發處理衝突。
- 系統制式模板（幻覺驗證失敗核准後用來取代 LLM 文字的樣板）需要在實作階段設計。

## 2026-08-24 [標籤：AI] 修正：供應商模糊比對案件核准後的接回方式

**狀態**：accepted

**背景**：SPEC.md 通讀檢查時發現，上一篇「待人工複核佇列的處理者、接回主流程方式與通知範圍」決策 2 裡，供應商模糊比對案件寫「流程從查詢供應商報價那一步繼續，不重跑 LLM 解析」，這句話有邏輯錯誤：對照系統主流程順序，Mask 節點在 LLM 解析節點**之前**執行，模糊比對是在 Mask 節點階段被攔下、流程中止，代表 LLM 根本還沒有機會解析出「品項、數量、幣別」。這些欄位在中止當下並不存在，管理員確認供應商身分後無法直接跳到「查詢供應商報價」，因為系統還不知道要查哪個品項、查多少數量。

**討論內容**：唯一合理的接回方式是：管理員確認供應商身分後，用確認後的供應商產生 Token，把原始文字重新送進 Mask→LLM 解析節點，走一次完整的正常遮罩→解析流程（此時品項/數量/幣別才第一次被解析出來），而不是跳過解析。

**決策**：
1. 修正 FR-6a：供應商模糊比對案件核准後，用確認後的供應商產生 Token，重新走正常遮罩→LLM 解析流程；不再寫「不重跑 LLM 解析、跳到查詢供應商報價」。
2. 對照修正 SPEC.md 例外處理表對應那一列的說明文字。

**理由**：修正邏輯錯誤，避免實作時卡在「品項/數量從哪裡來」這個無解問題。

**後果**：
- `docs/specs/SPEC.md` FR-6a 與例外處理表已同步修正。
- 幻覺驗證失敗案件的接回方式（用系統制式模板取代摘要文字、直接接續簽核流程）不受影響，因為該案件在中止前已經完整跑過解析、查詢、試算，只有生成摘要文字這一步有問題，不需要重跑解析。

## 2026-08-24 [標籤：使用者] 簽核金額門檻與層級設計

**狀態**：accepted（決策 2 已於 2026-08-24 被 `docs/ADR/discuss/db-schema.md` 取代，見下方標註）

**背景**：原始構想文件只寫「Django service：依金額判斷簽核層級」，沒有定義分幾層、門檻金額多少、每層對應誰，開發前必須先定案。

**討論內容**：
- 分層數：討論二層 vs 三層，決定用三層（小額／中額／大額），因為兩層看不太出「依金額路由」機制的示範效果。
- 門檻金額：因為是 demo 系統，不套用特定公司財務規範，決定金額門檻直接寫死在 Django 設定，先抓合理示範值（1 萬、10 萬），面試時可說明「目前寫死示範，真實導入時依公司財務規範調整」。
- 層級對應方式：討論「三層角色各自對應職稱（部門主管/財務主管/總經理）」vs「不新增角色，改用金額上限欄位」。前者更貼近真實企業職稱但會讓權限模型變複雜（需要在簽核人角色下再分等級）；後者維持現有三種角色（員工/簽核人/管理員）不變，只在使用者資料上加欄位。決定採用後者，簡化權限模型。
- 找不到符合門檻的簽核人：金額超過所有簽核人上限時，決定路由給管理員，管理員視為金額上限無上限。

**決策**：
1. 簽核層級分三段：小額（1 萬元以下）、中額（1 萬～10 萬元）、大額（10 萬元以上），門檻金額寫死在 Django 設定。
2. ~~不新增子角色，於使用者資料表新增「簽核金額上限」欄位，簽核人角色底下不同使用者可設定不同上限；管理員視為金額上限無上限。~~ **【superseded，2026-08-24】** 建立 DB schema 時使用者改要求把角色與金額上限正規化成獨立 `roles` 表，角色不再限於 3 種固定值、改用多種細分角色各自帶固定金額上限來達成「不同簽核人不同上限」的效果。完整討論與新決策見 `docs/ADR/discuss/db-schema.md`。
3. 路由邏輯：找出「簽核金額上限 ≥ 該筆採購金額」中，上限最低的簽核人，作為對應簽核人；若無任何簽核人上限足夠，路由給管理員。（上限資料來源已依決策 2 的取代結果，改為查詢 `roles.approval_amount_limit`，邏輯本身不變）

**理由**：金額上限欄位比新增分層角色更簡單，權限模型維持三種角色不變，同時保留「不同人可以有不同簽核權限」這個貼近真實企業的設計，複雜度落在資料欄位而不是角色架構。

**後果**：
- 使用者資料表需新增「簽核金額上限」欄位（數字，可為 null 表示無上限，管理員固定視為無上限）。
- Django service 需實作「依金額找出上限最低但足夠的簽核人」查詢邏輯。
- 門檻金額（1 萬/10 萬）與各簽核人的上限值屬於種子資料/設定，非使用者可自行調整的正式功能，如需開放後台調整可另外記入 DRAFT.md 討論。

## 2026-08-24 [標籤：使用者] 技術棧版本鎖定策略

**狀態**：accepted

**背景**：SPEC.md 技術棧表格版本欄原本全部是空的，需要決定要不要鎖精確版本、鎖到什麼粒度。

**討論內容**：查詢當下（2026-08-24）各技術的最新公開版本：Django 6.1（2026-08-05）、Django REST Framework 3.18.0（2026-08-07）、PostgreSQL 18 系列（最新小版本 18.6）、djangorestframework-simplejwt 5.5.1、n8n 2.36（自架 Docker，2026-08-18）。Vue／Vite／Pinia 的 npm 版本頁面為動態載入，查證可靠度不足，不採信查到的數字。討論後認為 SPEC.md 是「不常變動的定案文件」，寫死精確 Patch 版號容易在專案開發過程中就過時，反而需要頻繁修訂 SPEC；精確版本本來就該由套件管理工具的 lockfile（`requirements.txt`／`package.json`）當作真相來源。

**決策**：
1. SPEC.md 技術棧表格版本欄只鎖大版本（Major/Minor），不鎖精確 Patch 版號：Vue 3.x、Vite 6.x、Pinia 2.x、Django 6.x、DRF 3.18+、PostgreSQL 18.x、djangorestframework-simplejwt 5.5.x。
2. n8n、LLM API（Gemini/Groq）不鎖版號，因為屬於持續更新的自架服務/外部 API，鎖版號沒有實質意義。
3. 實際安裝時的精確版本，由 `requirements.txt`／`package.json` 的 lockfile 決定，不重複寫進 SPEC.md。

**理由**：避免 SPEC.md 因套件版本迭代而頻繁需要修訂，版本鎖定的真相來源交給本來就該負責這件事的套件管理工具；同時避免把查證可靠度不足的版本號（如本次 Vue/Vite/Pinia 查到的疑似過期資料）寫進正式定案文件誤導後續開發。

**後果**：
- Phase 1 開發時，`pip install`／`npm install` 安裝的實際版本即為專案採用版本，寫入 lockfile。
- 若日後需要記錄「目前實際採用的精確版本」，屬於技術現況，應放進 `docs/reference/`，不放 SPEC.md。

## 2026-08-24 [標籤：使用者] 部署方式：是否部署到 Render/Vercel

**狀態**：accepted

**背景**：原始構想文件的技術棧表格寫「Docker + Render/Vercel」，但這是一個模擬企業情境的展示型專案（面試用），不是要正式上線的產品，需要確認是否真的需要部署到公開雲端平台。

**討論內容**：比較「部署到 Render/Vercel」vs「Docker Compose 本地一鍵啟動＋demo 影片/截圖」。部署到公開平台的好處是面試官可以隨時自己連上網址操作；但成本是：系統橫跨 Vue／Django／n8n／PostgreSQL 四個服務，需要處理正式環境環境變數、跨服務網路、HTTPS；n8n 在免費方案容易休眠，面試官點開時可能要等重啟，觀感不佳；LLM API Key、Gmail OAuth、webhook 端點公開曝露會有濫用風險，而這個 demo 系統不會做完整的流量控管。原本排程（Phase 7／舊八天計畫 Day 7）已經規劃「Docker Compose 一鍵啟動」＋ Day 8「錄 demo 影片/截圖」，對面試情境來說已經足夠證明系統能跑起來。

**決策**：
1. 不部署到 Render/Vercel 等雲端平台，技術棧表格「部署」列改為「Docker Compose（本地一鍵啟動）」。
2. 展示方式維持原計畫：`docker compose up` 本地啟動＋demo 影片/截圖。
3. 未來若有需要（例如想讓面試官即時互動），可再評估是否部署，暫記入 `docs/specs/DRAFT.md` 擱置項目。

**理由**：這是展示型 demo 專案，不是正式產品，公開部署的維運與安全成本跟「範圍原則：廣度優先，深度夠用即可」的精神衝突，且會排擠時間到真正想展示的遮罩／幻覺驗證這兩個技術亮點上。

**後果**：
- SPEC.md 技術棧表格「部署」列與備註同步更新。
- 舊排程 Day 6～8（原本含 Render/Vercel 部署相關工作）不需再規劃雲端部署步驟，聚焦本地 Docker Compose 整合與 demo 準備。

## 2026-08-26 [標籤：使用者] 修正：一般簽核路由的單點失聯風險，比照複核佇列改用廣播＋認領

**狀態**：accepted

**背景**：SPEC.md 通讀檢查時發現，FR-7a 原本寫「找出上限最低但足夠的角色，取該角色底下的使用者作為對應簽核人」，但沒定義同一角色底下有多個使用者時該指派給誰，`approvals.approver_id` 又是 not-null 直接指定一個人。這代表：(1) 案件建立當下就得決定一個特定人選，邏輯不完整；(2) 萬一被指派到的那個人剛好沒空，完全沒有像 FR-6b 複核佇列那樣的防呆機制，案件會卡住——這跟先前「管理者剛好沒空」的疑慮是同一類風險，卻只有複核佇列解決了。

**討論內容**：既然複核佇列的「通知所有管理員＋認領機制」已經驗證過可以低成本解決單點失聯風險，一般簽核路由沒有理由用不同的處理方式。決定直接套用同一套模式：案件建立時只決定「路由到哪個角色」，不預先指定特定人；該角色底下所有使用者都收到通知；誰先認領誰處理。

**決策**：
1. 修正 FR-7a：路由邏輯找到對應角色後，將案件指派給該角色（新增 `approvals.role_id` 欄位），不預先指定特定使用者。
2. 修正 FR-8：Gmail 通知範圍改為該角色底下所有使用者（廣播），而非單一人。
3. 新增 FR-8a：簽核佇列頁面提供認領機制，`approvals.approver_id` 改為 nullable，認領當下才寫入；已認領案件對同角色其他使用者顯示認領狀態，避免衝突決議。
4. FR-9 調整為「簽核人認領案件後」才能執行核准/駁回。

**理由**：複核佇列與一般簽核路由本質上是同一類「案件指派給一群有資格的人，但不知道誰有空」的問題，用同一套廣播＋認領模式解決，面試時也能說成一致的容錯設計，不需要為兩種案件維護兩套不同邏輯。

**後果**：
- `docs/specs/SPEC.md` FR-7a、FR-8 改寫，新增 FR-8a，FR-9 補上「需先認領」；例外處理與邊界條件表新增對應列。
- `docs/reference/db_schema.md` 的 `approvals` 表新增 `role_id`（FK → roles.id），`approver_id` 改為 nullable。
- Django service 的簽核路由邏輯與 Vue 簽核佇列頁面的認領 UI 屬於實作階段任務，記入 PROGRESS.md 追蹤。

## 2026-08-27 [標籤：AI] 修正：manual_review_queue.quote_id 改為 nullable

**狀態**：accepted

**背景**：Phase 3 開工前重讀文件，發現 `docs/reference/db_schema.md` 把 `manual_review_queue.quote_id` 標記為 NOT NULL，但這跟本檔前一則「修正：供應商模糊比對案件核准後的接回方式」的定案互相矛盾——該決策確立 `supplier_fuzzy_match` 案件是在 Mask 節點階段（LLM 尚未解析出 product/quantity/currency，`quotes` 表其餘欄位皆 NOT NULL）就建立複核紀錄，此時根本不可能有 Quote 資料列可供 `quote_id` 指向。

**討論內容**：兩個方案——(a) 讓 `quote_id` 允許 null，`supplier_fuzzy_match` 案件靠既有的 `raw_input_text` 欄位保留原始輸入；(b) 改變流程，讓 Mask 節點先建立一筆不完整的 Quote 再指向它。(b) 會讓 `quotes` 表出現大量欄位缺值的暫存列，污染「已核准歷史均價」等查詢邏輯，且違反 `quotes` 表欄位設計的本意；(a) 只是欄位屬性調整，不影響其他設計，且 `raw_input_text` 欄位本來就是為這個案件類型準備的。採用 (a)。

**決策**：
1. `manual_review_queue.quote_id` 改為 nullable：`supplier_fuzzy_match` 案件 `quote_id` 為 null，靠 `raw_input_text` 保留原始輸入；`hallucination_mismatch` 案件（此時 Quote 已存在）照樣填值。
2. Django migration：`apps/audit/migrations/0002_alter_manualreviewqueue_quote.py`。

**理由**：維持「案件在流程哪個階段建立，就只依賴當下已存在的資料」的一致性，避免為了遷就 schema 約束而在流程中塞入不完整的 Quote 列。

**後果**：
- `apps/audit/models.py` 的 `ManualReviewQueue.quote` 欄位加上 `null=True, blank=True`。

## 2026-08-27 [標籤：使用者] 供應商模糊比對案件核准後，交還 n8n 流程的通知機制

**狀態**：accepted

**背景**：`supplier_fuzzy_match` 案件經人工在 `manual-review-queue/{id}/decide/` 核准（確認供應商身分）後，需要重新走一次「遮罩金額→LLM 解析品項/數量→查詢供應商/產品→試算→摘要→幻覺驗證」，才能真正產出報價。這段串接原本開工時被誤歸類為「非本次 Phase 範圍」寫進 PROGRESS.md 已知待補，但重讀 SPEC.md 後確認 FR-6a 明確要求「確認為系統疑似比對到的供應商...重新走正常遮罩→LLM解析流程」，屬於 Phase 3 範圍內、只是這次開發本身漏做，因此補上設計與實作。核心問題：Django 核准決議完成後，n8n 要怎麼知道「這個案件已核准、可以繼續」？

**討論內容**：兩個方案——(a) Django 核准後主動呼叫 n8n 的一個新 Webhook（例如 `/webhook/inquiry/resume`），把 `review_id`／`raw_input_text`／`user_id`／`supplier_id` 當作 payload 帶過去；(b) n8n 用排程節點（Cron/Interval）定期輪詢 `manual-review-queue`，找出剛核准的 `supplier_fuzzy_match` 案件。(b) 需要在 `manual_review_queue` 上加一個「是否已被 n8n 撈取過」的狀態欄位避免重複處理，且引入輪詢延遲（不是即時），架構上多一層複雜度；(a) 是事件驅動、即時觸發，且 n8n 主流程本身就是靠 Webhook 觸發，風格一致，不需要額外狀態欄位。使用者選擇 (a)。

**決策**：
1. Django 主動呼叫 n8n 新增的 `N8N_RESUME_WEBHOOK_URL`（`/webhook/inquiry/resume`），在 `manual_review_service.decide_review()` 核准 `supplier_fuzzy_match` 案件、DB 交易確定提交後呼叫，帶 `review_id`／`raw_input_text`／`user_id`（原始詢價發起人，非核准者）／`supplier_id`。
2. n8n 呼叫失敗（連線問題、逾時、非 2xx）不影響核准決議本身——DB 裡供應商已確認的事實不因外部呼叫失敗而回滾；`decide_review()` 回傳值多一個 transient 欄位 `resume_triggered`（非 DB 欄位）讓 API 層告知呼叫端是否成功觸發，供前端視需要顯示「已核准但通知續傳失敗，請手動確認」之類的提示。
3. 為了讓 n8n 續傳流程知道「原始詢價發起人是誰」，`manual_review_queue` 新增 `requester` 欄位（FK → users，migration `0003_manualreviewqueue_requester`），`masking_service.mask_text()` 建立複核紀錄時一併填入。
4. 續傳流程只需重新遮罩金額（供應商已由人工確認，不需要再猜），新增 `masking_service.mask_amounts_only()` 與對應端點 `POST /masking/mask-amounts-only/`，供 n8n 續傳子流程呼叫。

**理由**：事件驅動比輪詢更符合系統既有的 Webhook 觸發風格，也不需要額外的「已處理」狀態欄位；核准這個動作的正確性（DB 交易）與「通知下游繼續處理」這個動作的可靠性分開處理，避免外部系統暫時不可用時把已經確認為真的人工決議也一併回滾。

**後果**：
- `apps/audit/models.py`：`ManualReviewQueue` 新增 `requester` 欄位。
- `services/inquiry_resume_service.py`（新檔）：`trigger_resume()`。
- `services/manual_review_service.py`：`decide_review()` 核准 `supplier_fuzzy_match` 時呼叫 `trigger_resume()`。
- `services/masking_service.py`：新增 `mask_amounts_only()`。
- `api/audit/views.py`／`api/audit/urls.py`：新增 `MaskAmountsOnlyView`（`POST /masking/mask-amounts-only/`）。
- `config/settings.py`／`.env.example`：新增 `N8N_RESUME_WEBHOOK_URL`。
- `n8n/workflows/inquiry-flow.json`：新增「續傳子流程」14 個節點（`Webhook 續傳詢價` 起始），節點數 19→33，本機驗證過程與發現的 bug 見 `docs/ADR/debug/n8n-workflow-authoring-issues.md`。
- `docs/reference/api.md`：補上新端點與 `decide` 回應新增的 `resume_triggered` 欄位。
