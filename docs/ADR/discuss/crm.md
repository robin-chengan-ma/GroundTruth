# CRM 模組 討論紀錄

> 同一功能的多次討論都寫在同一個檔案，依時間往下附加新段落，不要開新檔案。

## 2026-08-26 [標籤：使用者] 歷史報價異常比對：補上 CRM 模組承諾但主流程未串接的功能

**狀態**：accepted

**背景**：SPEC.md 通讀檢查時發現，CRM 模組概要與舊版 FR-2 承諾「保留歷史採購紀錄供系統比對異常報價」，但系統主流程（`docs/ADR/discuss/main-flow.md`）從頭到尾沒有任何一步真正做「歷史報價比對」，是一個承諾了卻沒有串接進主流程的功能缺口。

**討論內容**：使用者直接指定了實作方式：試算完報價後，額外查一次該供應商＋該品項的歷史成交均價，如果這次金額偏離超過某個百分比，也連同幻覺驗證一起附註在複核佇列或稽核 log 上，讓管理員或稽核總覽頁能看到「這筆比歷史行情貴 30%」。討論後決定不把價格異常標記當成阻斷流程的條件（跟幻覺驗證不同，幻覺驗證是「AI 說謊」的信任問題，價格異常只是「這筆比較貴，但不代表有錯」的資訊性提示），因此不強制進入待人工複核佇列，只做視覺標記，避免正常但單純市場波動大的報價也被卡流程。

**決策**：
1. 新增系統主流程 FR-4a：試算完成後，Django service 查詢該供應商＋該產品過去**已核准**採購單的平均單價，計算本次單價偏離百分比，寫入 `quotes.price_deviation_pct`；偏離超過門檻（20%，寫死於 Django 設定）標記為價格異常。
2. 該供應商＋產品組合過去無已核准紀錄時，視為無法比較，`price_deviation_pct` 記為 null，不標記異常、不中止流程。
3. 價格異常僅供簽核人查看頁面（FR-9）與稽核總覽模組呈現，不阻斷流程、不強制進入待人工複核佇列，跟幻覺驗證的「阻斷式」處理方式明確區分。
4. CRM 模組 FR-2 改寫為：保留歷史採購紀錄（即 `quotes` 表本身），供主流程 FR-4a 查詢使用；供應商的「最後成交時間」等狀態不另外新增欄位儲存，需要時直接查詢 `quotes` 表即時算出（呼應 AGENTS.md 資料庫設計原則：不重複儲存可由既有欄位查詢得到的資料）。

**理由**：只比對「已核准」的歷史紀錄，才能反映真實成交行情，避免被中止/駁回的異常報價汙染均價；不阻斷流程是因為「比歷史行情貴」本身不代表有錯（例如市場波動、供應商臨時漲價都合理），跟幻覺驗證這種「AI 生成內容與真實數字不符」的信任問題性質不同，不該用同一套阻斷邏輯處理。

**後果**：
- `docs/specs/SPEC.md` 系統主流程新增 FR-4a、流程圖新增一步「比對歷史均價」，CRM 模組 FR-2 改寫，稽核與正確率總覽模組新增 FR-4（呈現價格異常統計）。
- `docs/reference/db_schema.md` 的 `quotes` 表新增 `price_deviation_pct`（decimal，nullable）欄位。
- 例外處理與邊界條件表新增一列：無歷史紀錄可比較時的處理方式。

## 2026-08-26 [標籤：使用者] 補充：LLM 生成摘要文字不含價格異常資訊

**狀態**：accepted

**背景**：SPEC.md 通讀檢查時發現，FR-4a／FR-5／FR-9 沒有明確講清楚「價格異常」這個資訊會不會被塞進 LLM 生成的報價摘要文字裡。如果 LLM 摘要文字意外提到「這筆比歷史行情貴 30%」，那幻覺驗證（FR-6）要不要連這個數字也一併驗證，屬於未定義行為。

**討論內容**：確認 FR-4a 的價格異常設計目的是給簽核人與稽核總覽頁「另外看到」的資訊性標記，不是報價摘要文字本身要傳達的內容；因此明確排除價格異常資訊進入 LLM 摘要生成的輸入，避免它意外混進摘要文字後，落入幻覺驗證邏輯的灰色地帶。

**決策**：
1. `quotes.price_deviation_pct` 不作為 FR-5（LLM 生成摘要文字）的輸入資料。
2. 價格異常僅由前端另外查詢 `quotes.price_deviation_pct` 欄位顯示（FR-9），不在 FR-6 幻覺驗證的比對範圍內。

**理由**：讓「報價金額試算」（幻覺驗證覆蓋範圍）與「價格異常提示」（資訊性標記）維持職責分離，避免驗證邏輯的比對範圍隨著 LLM 摘要文字的措辭變化而模糊。

**後果**：
- `docs/specs/SPEC.md` FR-4a 補上排除說明。
