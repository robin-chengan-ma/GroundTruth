# Phase 5 安全與應用切換修復紀錄

## 2026-08-31 n8n v2 候選解析繞過敏感資料遮罩
**現象**：新版 `inquiries/parse/` 雖只回傳候選資料且不建單，但 Django 將使用者 `raw_text` 原文直接送到 n8n／Gemini；多間供應商名稱與具金額語境的數字未經 Phase 3 固定遮罩。
**排查過程**：沿 `InquiryCandidateParseView → parse_purchase_request_candidate() → request_candidate_parse()` 檢查資料流，確認 Service 未呼叫 masking service，Repository 直接以原文建立 webhook payload。另確認既有 `mask_text()` 專為 legacy 單供應商流程設計，兩間完整命中的供應商會被視為歧義，不能直接重用於新版多候選流程。
**根因**：D2 建立新候選解析契約時只分離「AI 候選」與「正式建單」，沒有把 FR-2／NFR-1 的遮罩邊界一併移植到新 webhook；因此形成新舊流程安全能力不一致。
**修復方式**：在 `backend/services/masking_service.py` 新增新版專用 `mask_candidate_text()`，將所有完整命中的已建檔供應商與金額 Token 化；顯式供應商片段混有未知名稱時採 fail closed，完全未知沿用查無分流，模糊命中沿用人工複核。新增 `unmask_payload()` 遞迴還原 n8n 回傳的巢狀候選字串。`backend/services/inquiry_service.py` 改為遮罩成功後才呼叫 Repository，mapping 只留在單次函式呼叫記憶體。
**驗證方式**：TDD RED 確認多供應商／金額仍以原文送出及遞迴還原函式不存在；GREEN 驗證單一與多供應商、金額、巢狀 payload、未知供應商、混合已知／未知、空值、Malformed payload 與 API 權限。目標測試、完整回歸、coverage、Ruff、Django check、Migration check 於 PROGRESS 記錄最終結果。
**未驗證範圍**：無。Robin 已以真實 n8n production webhook 從 Vue 驗證兩間供應商、兩品項與預算情境：LLM Input 僅含 `SUP_001`／`SUP_002`／`AMOUNT_001`，不含真實供應商名稱與金額；LLM Output 保留供應商 Token，Django 正確還原兩間候選供應商。workflow JSON 依 ignore／敏感資料規則不由 AI 讀取或修改。

## 2026-09-01 接手中斷的 Phase 5：查詢契約缺口與撤回狀態機 bug
**現象**：接手前一個 AI 工具中斷的 Phase 5 工作前，先建立基線盤點，發現三類問題：①`InventoryViewSet` 用 `AuthenticatedReadAdminWrite`（等同任何 `master_data.read` 的人都能查庫存），與庫存查詢應有專屬權限的設計不一致；②`ApprovalStep` 的 `claim`／`decide` 對「需求已被撤回」的案件沒有狀態防線；③撰寫 ②的 regression test 時（`test_claim_step_rejected_after_request_withdrawn_cancels_case`），測試在到達預期的 `ApprovalWorkflowConflict` 之前就先炸出 `django.db.utils.IntegrityError: ... violates check constraint "award_decisions_submission_time_consistent"`。
**排查過程**：①②為唯讀盤點直接發現，非除錯。③一開始懷疑是測試 fixture 沒有正確把 `AwardDecision` 提交（`submitted_at` 為空）才觸發 constraint，但追蹤 `purchase_request_draft_service.withdraw_request()` 的實際邏輯後確認：任何一筆「已進入 AWARDING 狀態、但得標決議尚未走完提交流程」的真實採購需求被撤回時，都會呼叫同一段「取消得標決議」的 `.update()`，同樣會在正式環境撞上這個 DB constraint——不是測試資料不真實，是測試資料照實還原了一個目前生產程式碼本來就會炸掉的路徑。
**根因**：①`InventoryViewSet` 建立時圖方便沿用了主資料的粗粒度權限類別，未依庫存查詢的實際敏感度另外分權限碼。②`claim_step`／`decide_step` 只檢查關卡本身狀態，沒有檢查其所屬 `ApprovalCase`／需求是否仍在有效流程中。③`withdraw_request` 取消得標決議時直接把 `status` 設為 `cancelled` 並 `.save()`，但 `AwardDecision` 的 DB CHECK constraint 要求「非 draft 狀態時 `submitted_at` 不得為空」，撤回邏輯完全沒考慮「得標決議還沒提交」這個中間狀態。
**修復方式**：①`backend/api/erp/views.py`：`InventoryViewSet` 改用 `HasPermissionCode`＋`required_permission = "inventory.read"`；同步在 `admin_user` fixture（`tests/conftest.py`）與 `seed_demo_data.py` 補上這個新權限碼。②`backend/services/approval_case_service.py` 新增 `_ACTIVE_CASE_STATUSES`／`_ensure_case_active(case)`，在 `claim_step`／`decide_step` 內以 `select_for_update()` 先鎖定 case 再檢查，不符合時拋 `ApprovalWorkflowConflict`（API 層回 409）。③`backend/services/purchase_request_draft_service.py`：取消得標決議前用 `Coalesce(F("submitted_at"), Value(timezone.now()))` 補齊送出時間，一次 `.update()` 內同時補時間與轉態，不覆寫既有值。
**驗證方式**：新增 6 個測試（含 1 個鎖定 constraint bug 的專屬 regression test）。TDD RED 確認①未授權查庫存會通過、②撤回後仍可認領／決議、③撤回會噴 IntegrityError；GREEN 全部通過。完整回歸 Backend 349→354 passed，Ruff、`makemigrations --check --dry-run`、`manage.py check` 通過，已用 SHA-256 雙邊校驗同步回裝置（見 PROGRESS.md 對應列）。
**未驗證範圍**：Robin 尚未在真實瀏覽器／n8n 環境重新走一次庫存查詢與撤回流程；僅完成後端自動測試驗證。

## 2026-09-01 RFQ／供應商報價／得標決議缺少查詢契約，供應商品項與版本價格完全沒有 API
**現象**：延續同一次基線盤點，發現 `RfqViewSet`／`SupplierQuoteViewSet`／`AwardDecisionViewSet` 三個 ViewSet 完全沒有定義 `list`／`retrieve` 方法；DRF `DefaultRouter` 只會依 ViewSet 實際定義的方法產生對應路由，因此 `GET /api/v1/rfqs/`、`GET /api/v1/supplier-quotes/`、`GET /api/v1/award-decisions/` 及其 `{id}/` 版本並非回 404，而是路由本身就不存在。另外盤點 `apps/procurement/models.py` 發現 `SupplierProduct`／`SupplierPriceVersion`（供應商可供應品項與版本化價格）已有完整 Model、DB constraint 與既有 `repositories/procurement.py` 內部查價邏輯依賴這兩個 Model，但完全沒有對外 REST API——沒有任何 endpoint 可以建立、查詢、啟用／停用供應商品項關係或新增價格版本。
**排查過程**：唯讀盤點 `api/procurement/views.py`、`api/procurement/urls.py` 與 `apps/procurement/models.py` 直接發現，非執行期錯誤觸發的除錯。
**根因**：這兩類缺口都源自先前的開發流程只從「業務動作」（送出報價、決標、簽核）角度補齊 command API，沒有從「SPEC.md 明列的查詢契約清單」逐項核對，導致三個資源的查詢路由與供應商品項這整個資源都被遺漏。
**修復方式**：①新增 `RfqRepository.accessible()`／`SupplierQuoteRepository.accessible()`／`AwardRepository.accessible()`（皆含對應 `select_related`／`prefetch_related`），在 `rfq_quote_service.py`／`award_selection_service.py` 補上 `_require_*_read_permission`／`list_accessible_*`／`get_accessible_*`，並在對應 ViewSet 補上 `list`／`retrieve`。②新增 `SupplierProductRepository`（含新增價格版本前的時間重疊查詢 `overlapping_price_versions()`）、新檔 `services/supplier_product_service.py`（`master_data.read`／`master_data.manage` 權限分流；主檔只能啟用／停用不得實體刪除，回 409／`physical_delete_forbidden`；價格版本只能新增不得覆寫既有版本，新增前檢查同幣別／數量級距是否已有時間重疊的有效版本，重疊回 409）、`schemas/procurement.py` 新增對應 Serializer、`api/procurement/views.py` 新增 `SupplierProductViewSet`（含 `POST {id}/price-versions/` action）並在 `urls.py` 註冊 `supplier-products` 路由。
**驗證方式**：查詢契約補齊新增 11 個測試（`tests/test_phase5_query_contracts.py`），供應商品項 CRUD 新增 6 個測試（`tests/test_phase5_supplier_product_crud.py`），皆先 RED 後 GREEN。完整回歸 Backend 354→371 passed，Ruff（自動修正 3 個 `FURB157` 冗長 `Decimal()` 寫法後重跑確認仍全過）、`makemigrations --check --dry-run`（No changes detected）、`manage.py check`（0 issues）通過，已用 SHA-256 雙邊校驗同步回裝置（見 PROGRESS.md 對應列）。
**未驗證範圍**：Robin 尚未在真實瀏覽器環境操作供應商品項與價格版本維護（目前無對應前端頁面，屬 Phase 6 範圍）；`QuoteRequirementResultViewSet` 確認維持不需要獨立 `list`／`retrieve`（透過 `SupplierQuote` 詳情的 `items__requirement_results__requirement` 已可查詢，未發現獨立查詢需求），未另外補測試驗證此一設計判斷本身。

## 2026-09-01 收斂 DRAFT.md 兩個待決項目：purchase_suggestion.read 權限碼與 legacy service 移除
**現象**：前一輪盤點記錄了兩個待 Robin 決定的項目（`PurchaseSuggestionViewSet` 權限碼選擇、5 個已無引用的 legacy service 是否移除），Robin 一次核准兩項並要求直接執行，不要求分次確認。
**排查過程**：非除錯，屬已核准決策的直接落地。
**修復方式**：①`PurchaseSuggestionViewSet` 新增 `get_permissions()`：`list`／`retrieve` 改用 `HasPermissionCode`／`required_permission = "purchase_suggestion.read"`；`convert`／`dismiss` 維持 `IsAuthenticated`，授權仍交給 service 層既有的 `purchase_request.create`／admin 身分檢查，避免把「能看」與「能轉單／忽略」兩種能力混在同一個權限碼上（若直接對整個 ViewSet 套用單一 `HasPermissionCode`，會連帶擋下 `convert`／`dismiss`，這點在寫 RED 測試時被實際測出來，不是憑空推測）。`seed_demo_data.py` 的 `employee`／`admin` 角色補上這個新權限碼，`conftest.py` 的 `admin_user` fixture 同步補上。②確認 `approval_service.py`、`approval_routing_service.py`、`hallucination_check_service.py`、`quote_calculation_service.py`、`quote_summary_template.py` 及其專屬 legacy 測試檔（`test_approval_service.py`、`test_hallucination_check_service.py`、`test_quote_calculation_service.py`）無生產程式碼引用後移除；`tests/test_api_phase4.py` 移除對 `approval_routing_service.route_quote` 的測試資料建置依賴（該測試驗證的是 410 回應本身，不需要這段 setup）。

**驗證方式**：新增 3 個測試（`test_purchase_suggestion_list_requires_dedicated_permission`、`test_purchase_suggestion_list_and_retrieve_visible_with_permission`、`test_purchase_suggestion_convert_and_dismiss_not_gated_by_read_permission`），先 RED 後 GREEN；移除 5 個 legacy service 後完整回歸 371→330 passed（減少的 41 個測試皆為被移除 service 的專屬單元測試），新增 3 個權限測試後 330→333 passed。Ruff、`makemigrations --check --dry-run`、`manage.py check` 皆通過。前端同步完成 `/quotes`→`/purchase-requests`、`QuoteListView.vue`→`PurchaseRequestListView.vue` 改名（`router/index.ts`、`navigation.ts`、`views/InquiryView.vue`、`tests/purchase-request-list.spec.ts` 一併更新），於裝置本機的 Linux VM 因 `node_modules` 是在 macOS 上安裝、`@rollup/rollup-linux-arm64-gnu` 缺失而無法直接執行 `vitest`／`vite build`，改為把 `frontend/src` 連同設定檔（不含 `node_modules`／`dist`）暫存進雲端環境、以 `pnpm install --frozen-lockfile` 重新安裝依賴後驗證：`vitest run` 25 passed、`vue-tsc -b` 無錯誤、`eslint .` 無錯誤、`vite build` 成功；裝置端與雲端驗證版本已用 SHA-256 逐檔比對一致。所有異動（含刪除／改名）已直接在裝置的實際檔案系統完成（`device_bash` 的沙箱不允許 `unlink`，改用同一檔案系統內的 `mv` 完成刪除與改名；`git mv`／`git add`／`git commit` 因 `.git/index.lock` 卡住的 stale lock 目前在該沙箱內無法寫入，不影響本次檔案異動本身，但代表 Robin 之後在自己機器上開一般終端機執行 `git add`／`git commit` 前，建議先確認沒有殘留的 `.git/index.lock`）。
